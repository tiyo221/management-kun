# metrics — プロダクト指標（KGI / NSM / KPI）（モジュール個別仕様）

統合上の位置づけ・共通マスタとの関係・固有データの所在を定める。共通の取り決め（アーキテクチャ・データ規格・名寄せ・デザイン）は [`spec.md`](../../spec.md)（共通仕様）を正とする。

- localStorage: `mk:module:metrics:<productId>:v1`（**product-scoped**・§3.7.4）
- ゾーン: **プロダクト**（releases に続く2つ目のゾーンモジュール。§1.4 / §1.5）
- 新規モジュール（旧ツールなし。product-scoped モジュールの初の実体化。Issue #168）

## 役割
対象プロダクトごとに、KGI（最上位のビジネス目標指標）← NSM（北極星指標・通常1つ）← KPI（支える先行/遅行指標）の**指標ツリー**を管理する。目標設定ツールというより「指標を木で整理し、実績を時系列で追う計測ダッシュボード」寄り。まず「指標を並べ、目標と実績と達成度を1画面で追える」ことを成立させ、トレンドの作り込み・複数粒度の併存は将来枠（§14）。

指標の削除は確認を出さず即実行し、`MK.ui.undoDeleteToast` で取り消せる（CONVENTIONS §2.5-3）。**削除の退避には引き上げた子の元の `parentId` も含める** ── 指標だけ戻して引き上げを巻き戻さないと、木が削除前と違う形になり「元に戻す」が嘘になるため（実績 `records` は指標に内包されるので指標ごと戻る）。confirm で伝えていた「子指標は親へ引き上げます」は、事後のトースト本文（例「削除しました（子指標2件を親へ移動）」）で伝える。`removeMetric` は**削除できたかを返す**（その id が無ければ `false`）ので、view は空振りではトーストを出さない。退避は他の変更に加えて**対象プロダクトの切替（`setStore`）でも破棄する**（scoped モジュールは対象ごとにデータセットが違う）。

## スコープと位置づけ（product-scoped）
- **Product スコープ次元（§3.7）の scoped モジュール**。`scope: { dim: "product" }` を宣言し、シェルが現在のプロダクトの対象別 store（`ctx.store`）を渡す。データはプロダクトごとに分離され、縮退モード（0=作成導線 / 1=畳む / 2+=スイッチャ）は `MK.scope` に従う。Product 次元の配線は #54 で済んでおり新インフラは不要（wbs の Project 次元・#25 と同じパターン）。
- これにより [`spec.md`](../../spec.md) §3.7.6 / §14 の「product-scoped モジュールの実体化は後続 Issue」を埋める。
- **他モジュールに依存しない**。参照するのは Product マスタ（`ctx.scope` 経由の対象プロダクト）のみ。goals（自分＝個人目標）・チーム OKR とは独立概念で、相互リンクしない（[`spec.md`](../../spec.md) §1.3 / §1.4 / §5.6）。いつでも単独で統廃合できる状態を保つ。

## 固有データ
- `metrics[]`: `{ id, name, kind, unit, direction, parentId, targetValue, records, note, createdAt, updatedAt }`。エンベロープは `{ version, metrics: [...] }`。
  - `name` = 指標名（必須）。
  - `kind` = 種別 = `kgi` / `nsm` / `kpi`（表示ラベルは KGI / NSM / KPI）。未知・未指定は `kpi` に正規化する。
  - `unit` = 単位（任意。例: %、円、人、件/月）。
  - `direction` = 方向 = `up`（大きいほど良い）/ `down`（小さいほど良い）。達成度判定に使う。未知・未指定は `up` に正規化する。
  - `parentId` = 親指標の id（トップは `null`）。KGI→NSM→KPI の階層を推奨するが**構造は強制しない自由木**。親削除時は子を親へ引き上げる（サブツリーごと消さない＝葉を失わない）。存在しない id を指す孤児はトップ扱いにして描画から漏らさない。付け替えは自分自身・自分の子孫を親にできない（循環拒否）。
  - `targetValue` = 目標値（未設定は `null`）。
  - `records[]` = `{ period, value }`。`period` は粒度1つ（月 `2026-07` または四半期 `2026-Q3`）を第一弾で採用し、同一 `period` は upsert（上書き）。同一粒度内は文字列の辞書順＝時系列順で「直近」を選ぶ。
  - `note` = メモ（任意）。
- モジュール内部 ID は `m_<epoch>_<rand>`（[`spec.md`](../../spec.md) §4.7）。

## 達成度（direction 考慮）
直近実績（最新 period の値）と `targetValue` から算出する（目標 or 実績が無ければ達成度は出さない）。

- `up`（大きいほど良い）: 達成 = 実績 ≥ 目標、比率 = 実績 / 目標。
- `down`（小さいほど良い）: 達成 = 実績 ≤ 目標、比率 = 目標 / 実績。
- 0 除算になる比率は出さない（達成可否のみ表示）。

## サマリー（HOME 表示）
`summary()` は product-scoped のため**全プロダクトを横断**して畳む（[`spec.md`](../../spec.md) §3.6・方針①③）。母数の羅列を避け、行動につながる指標を出す。

- stats: `達成 met/measured`（目標＋実績のある指標のうち達成できている数。計測中が無ければ `—`）／`未記録 N`（指標はあるが実績ゼロ＝最初の一手の母数）。
- attention: `未達 N件`（目標に届いていない指標・`warn`）。stats の達成と同一事実を二重表示しない。

モジュール自身のカード指標（表示中プロダクト単位の 指標数 / 達成 / 未記録）はビューが担い、本 `summary` は HOME 横断表示専用。

## 任意契約の採否（searchItems / summaryFor）
グローバル検索（[`spec.md`](../../spec.md) §3.5）と人／PJ 詳細の集約（§3.6.1）は任意契約。採否を固着させる（#220）。
- **searchItems**: 実装。全プロダクト横断で `label`＝指標名・`sub`＝プロダクト名+種別・`keywords`＝単位/メモを供給する。
- **summaryFor**: 見送り（保留）。指標は product エンティティに紐づくが summaryFor は人／PJ 対応が前提で、product 拡張は必要になった時点の後続 Issue に回す（#220 スコープ外・releases.md と同方針）。

## 第一弾スコープ外（必要になれば後続 Issue）
- CSV 入出力（releases 同様 v1 では持たない）。
- 他モジュール連携（例: releases との紐付け、KPI 自動集計）＝ Phase 3 クロス機能。
- 高度な可視化（トレンドのグラフ描画の作り込み・複数期間粒度の併存）。
